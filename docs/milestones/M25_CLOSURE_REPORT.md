# M25 Closure Report — Email Notification System

## Status: CLOSED

M25 gives the application its first real email channel: transactional and operational messages generated by three already-existing product events (registration, an appointment reminder becoming due, a Stripe billing failure/cancellation), delivered through Resend, with an honest, metadata-only delivery ledger. No marketing/campaign capability was built -- strictly transactional and operational email, per the approved scope.

## Problem Addressed

Before M25, the post-M24 audit found appointment/follow-up reminders existed only as in-app `Notification` rows -- a user who was not actively looking at the app inside a browser tab never received them anywhere. Registration produced no welcome message. A failed payment or an ended subscription produced no email at all, only an internal `BillingPayment`/`BillingSubscription` state change. `PRODUCT_ARCHITECTURE.md` §2.8 names email notifications explicitly, ahead of push ("Push notifications later") -- this was the single most-supported, highest-impact documented gap remaining after M24.

## Final Architecture

```
EmailNotification (Postgres): metadata-only ledger
  id, ownerUserId, category, eventType, recipientEmail, subject,
  status (pending -> sent | failed | skipped), idempotencyKey (unique),
  providerMessageId, failureCode, failureMessageSafe, attemptCount,
  relatedEntityType/Id, createdAt, sentAt, updatedAt
  -- the rendered body is never persisted.

sendTransactionalEmail (email-service.ts) -- the sole entry point:
  1. createPendingEmailNotification: durable "intent to send" row,
     status pending. An idempotencyKey collision returns the existing
     row (created: false) -- never a second row, never a second send.
  2. resolveEmailConfig: EMAIL_PROCESSING_MODE not "enabled", or a
     missing RESEND_API_KEY/EMAIL_FROM_ADDRESS -> status: skipped,
     provider never called.
  3. createResendEmailProvider().send(): the only network call. A
     non-2xx response, a timeout, or a 200 with no real message id all
     become status: failed with a distinct failureCode -- nothing is
     ever marked sent without a genuine provider-issued id.
  Deliberately never throws: every caller can await it without its
  own try/catch and never has its primary flow blocked.

Three real triggers (GO-3):
  - POST /auth/register success -> onboarding welcome email
  - executeDueAppointmentRemindersForOwner, only when it actually wins
    the claim on a new Notification row -> transactional reminder
    email to the owning professional (not the client -- clients have
    no account)
  - Stripe webhook invoice.payment_failed / customer.subscription.deleted,
    sent strictly after the DB transaction commits, never for a
    retried event (BillingWebhookEvent's existing providerEventId
    dedup returns before the email side-channel is ever set)

No retry (explicit M25 decision). No marketing/campaign path.
```

## Decisions Frozen in GO-1 and Honored Through GO-4

- **Resend as the provider**: confirmed by the user before GO-2; `email-provider.ts` is a small, swappable adapter behind the `EmailProvider` interface if this changes later.
- **No retry in M25**: held throughout; `attemptCount` exists in the schema for forward compatibility but the code never uses it beyond 0/1.
- **Only 2 Stripe events get email**: `invoice.payment_failed`, `customer.subscription.deleted` -- `created`/`updated`/`invoice.paid`/`checkout.session.completed` deliberately excluded, proven by test.
- **Reminder goes to the professional, not the client**: `Client` model was not touched; the only recipient resolution added is `findRecipientEmailForOwner(ownerUserId)`.
- **Metadata-only persistence**: no body/html/text column exists in the schema at all.

## Residual Risks (real, disclosed -- none block closure)

- **No live-Resend verification**: disclosed above. The `enabled` path is thoroughly unit-tested against a mocked HTTP response but has never made a real network call to Resend's servers in this environment. The first real send will happen only once `EMAIL_PROCESSING_MODE`/`RESEND_API_KEY`/`EMAIL_FROM_ADDRESS` are configured in a real deployment.
- **No automatic retry**: a transient provider failure (network blip, momentary Resend outage) results in a permanently `failed` row with no automatic recovery. Acceptable for M25 per the explicit decision; a future milestone can add retry based on real delivery data once the system has been live.
- **The rare double-DB-failure window**: if the database becomes unreachable between creating the `pending` row and updating it to its final status (an extremely narrow window, and the database must already be reachable to have created the row in the first place), that specific row could remain `pending` indefinitely. `sendTransactionalEmail` still never throws in this case -- the caller's return value is always accurate -- but the stored row could be stale. Not something a synchronous, non-transactional design across an external HTTP call can fully close.
- **Inherited FK risk**: `EmailNotification.ownerUserId` has the same hybrid dual-write dependency on `auth-persistence.ts` already disclosed for 11 other owned models since M22 -- not new to M25.
