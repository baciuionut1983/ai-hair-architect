# M28 Closure Report — Client CRM History Persistence

## Status: CLOSED

M28 migrates the professional-facing client CRM history — photos, color formulas, and treatment records — from an in-memory store (`milestone1-store.ts`) to durable PostgreSQL persistence, closing the last major in-memory gap in the client-data domain. No AI/model behavior, no authentication, no billing, and no M27 recommendation engine was touched anywhere in this milestone.

## Problem Addressed

The post-M27 global audit found that while `Client`, `Consultation`, `Appointment`, and `Analysis` were already durable in Postgres, the three CRM-history record types a stylist logs day-to-day — client photos, formulas used, and treatments performed — were still held in a plain in-memory array (`milestone1-store.ts`), lost on every server restart or deploy. This directly contradicted the product's own basic promise of being a client-record-keeping tool, and was judged the highest-impact remaining gap: unlike the M27 recommendation-engine gap (a missing *feature*), this was active data loss risk on a *production-critical path already in daily use*.

## Boundary: `ImageAsset` vs. `ClientPhoto`

These are, and remain, two deliberately separate systems:

- **`ImageAsset`** (M15/M18): object-storage-backed image used as input to the Gemini AI vision pipeline (`image-analysis-service.ts`). Belongs to the AI-analysis domain.
- **`ClientPhoto`** (M28): a CRM gallery entry — `imageUrl` + optional `caption` — logged by a stylist as part of a client's real service history. Belongs to the CRM domain.

M28 does not move, reuse, or couple these systems. `client-photo-repository.ts` and the `photos` route contain zero references to `ImageAsset`, the object-storage layer, or the Gemini pipeline (confirmed by direct grep in GO-4 verification). A future milestone could choose to let a CRM photo point at an existing `ImageAsset`, but no such linkage exists today.

## Boundary: AI Recommendation Plans vs. CRM History

`TechnicalCutPlan` / `ColorPlan` / `TreatmentPlan` (persisted on `Analysis`, M8/M27) remain immutable, AI-authored *recommendation snapshots*. `ClientPhotoRecord` / `FormulaRecord` / `TreatmentRecord` (M28) are real, professional-logged *history* — what a stylist actually did, entered by the stylist, not generated by AI. M28 introduces a single, optional, nullable `sourceAnalysisId` on `ClientFormula`/`ClientTreatment` as a pure traceability foundation:

- No CRM record is ever auto-created from an `Analysis`.
- No AI plan is ever edited, overwritten, or treated as proof a service was performed.
- No route, in this milestone, reads or writes `sourceAnalysisId` from any request — it exists in the schema and repository layer only, confirmed unused by both `formulas/route.ts` and `treatments/route.ts` (each has an explicit code comment stating this is deliberate and out of scope).
- Wiring an actual UI/flow that populates `sourceAnalysisId` is explicitly deferred to a future milestone.

## Final Architecture

```
client-photo-repository.ts / client-formula-repository.ts / client-treatment-repository.ts:
  Each exports createXForOwner + (formula/treatment only) listXForOwner,
  an XPersistenceError (503, DB unavailable) and an XDependencyError
  (404, client/sourceAnalysis not found or not owned -- both collapsed
  into one non-leaking outcome). Ownership is checked twice:
    1. Repository layer: tx.client.findFirst({ id, ownerUserId,
       deletedAt: null }) inside the same Prisma transaction as the write.
    2. Database layer: composite FK [clientId, ownerUserId] ->
       Client[id, ownerUserId] -- makes cross-owner association a
       database-level impossibility, not just an application check.
  Formula/Treatment additionally accept an optional sourceAnalysisId,
  cross-checked transactionally against Analysis(id, ownerUserId,
  clientId) when present, backed by the same composite-FK pattern
  ([sourceAnalysisId, ownerUserId, clientId] -> Analysis[id,
  ownerUserId, clientId], onDelete: Restrict).

Routes (src/app/api/v1/clients/[id]/...):
  photos/route.ts       POST only (unchanged contract -- reads happen
                         exclusively through /timeline)
  formulas/route.ts     GET + POST (unchanged contract)
  treatments/route.ts   GET + POST (unchanged contract)
  timeline/route.ts     GET -- folds listClientPhotosForOwner/
                         listClientFormulasForOwner/
                         listClientTreatmentsForOwner into the existing
                         Promise.all alongside consultations/appointments;
                         response shape, field names, and sort order
                         (createdAt desc, kind asc, id desc) unchanged.

milestone1-store.ts: the ClientPhotoRecord/FormulaRecord/TreatmentRecord
  imports, the photos/formulas/treatments Store fields, their
  initializers, their hot-reload guards, and all 6 functions
  (createClientPhoto, getPhotosForClientByUser, createFormulaRecord,
  getFormulasForClientByUser, createTreatmentRecord,
  getTreatmentsForClientByUser) were removed entirely. Every remaining
  export in the file was grep-verified to still have a live caller
  before GO-3 removed anything.
```

## Decisions Frozen in GO-1B/GO-2 and Honored Through GO-4

- **`onDelete: Restrict` on `sourceAnalysisId`** (not `SetNull`, which Prisma itself rejected as unsafe for this composite relation): an `Analysis` referenced by CRM history cannot be deleted until the link is explicitly removed in a future milestone. Explicitly approved as "accepted and desired, for traceability" — inert today since `Analysis` has no delete route.
- **Dual-layer ownership enforcement** (repository transaction + database FK), not solely a route-level check: honored identically across all 3 repositories.
- **No length-limit changes, no new UI, no contract renames**: confirmed via the empty `contracts.ts` diff across both GO-2 and GO-3.
- **Strictly additive migration**: the M28 migration contains exclusively `CREATE TABLE`/`CREATE INDEX`/`ALTER TABLE ... ADD CONSTRAINT` for the 3 new tables — zero `ALTER TABLE` on any pre-existing table, confirmed by grep in GO-2 and unchanged since.

## Residual Risks (real, disclosed — none block closure)

- **`sourceAnalysisId` has no populating flow yet**: the traceability foundation exists in the schema and repository layer, but no route, UI, or automatic process sets it. Linking a CRM record to the `Analysis` that informed it remains entirely manual/future work, deferred by explicit GO-1B decision.
- **In-memory session store is a pre-existing, unrelated characteristic of the whole application**, not something M28 introduced or is scoped to fix: any cookie-authenticated route loses its session on a server restart in this dev environment (persisted `Session` rows exist in Postgres via `createPersistenceSession`, but `getSession()` — used by every cookie-authenticated route including all 4 M28 routes — reads only the in-memory map). Login already handles this gracefully by lazily rehydrating the in-memory user record from Postgres, so a user simply re-authenticates; no data is lost. Flagged here for visibility, not as an M28 defect.
- **No UI**: this milestone is API/repository-layer only, consistent with the rest of the repository's current state.
- **Minor test-coverage asymmetry, disclosed in the GO-2 foundation audit**: only `client-photo-repository.integration.test.ts` has a dedicated real-Postgres ordering re-test; the formula/treatment integration suites rely on the byte-identical shared ordering query already proven once via photo. A completeness gap, not a functional risk.

## Out of Scope for M28

Linking AI-generated recommendations (`ColorPlan`/`TreatmentPlan`) to CRM history beyond the bare, unused `sourceAnalysisId` column — any UI, auto-suggestion, auto-population, or workflow that connects an `Analysis` to a `FormulaRecord`/`TreatmentRecord` — is explicitly out of scope for M28 and deferred to a future, separately-approved milestone.
